# zugrpc bug hunt, 2026-11-11

Commit `90cc3c0`. Hunters: 3 on Fable 5.2, run one at a time, none shown
another's report. Slices: (1) the R layer, (2) the gRPC wire boundary in
both directions, (3) lifecycle and ownership. Coordinator on Opus 5.5.
Built here: macOS (x86_64), R 4.6.2, zuhttp 0.1.0 with its
network-framework TLS backend, zuproto from its default branch. Counterparts:
three byte-scripted raw-framer h2c servers in Go (one per hunter and one for
the re-runs), grpc-go's interop server at v1.67.1, and `tools/test-server`.
Unverified: zuhttp's OpenSSL backend (Linux) and Windows (no fork there).
Nothing here ran over TLS, every counterpart was h2c, so TLS and ALPN
lifecycles are unverified.

The probe scripts are in `2026-11-11-bug-hunt-probes/`. `<W>` in them is
the hunt's scratch root, where `lib/` held a fresh install of `90cc3c0`.
The coordinator's re-runs are `coordinator-probes/h1.R`, `h2.R` and
`h3.R`, with `coordinator-srv/`. `target-map.md` is the map the hunters
were given. Every finding below was re-run by the coordinator against a
second fresh install of `90cc3c0`.

## 1. Resolve the stream's status with the unary resolver — #58, medium, reproduced

- Where: [R/stream.R:115-120](https://github.com/pedrobtz/zugrpc/blob/90cc3c0/R/stream.R#L115-L120)
  and [R/stream.R:266-287](https://github.com/pedrobtz/zugrpc/blob/90cc3c0/R/stream.R#L266-L287),
  against `unary_outcome()` in [R/call.R](https://github.com/pedrobtz/zugrpc/blob/90cc3c0/R/call.R).
- Trigger and observation, four cases, each the same bytes given to unary
  and to a stream:
  - **Header status after a body.** Headers carry `grpc-status: 0`, a
    message follows, and there are no trailers. Unary is `INTERNAL`
    (missing status). The stream ends `OK`.
  - **Body ends inside a message.** DATA `00 00000005 aa`, then trailers
    `grpc-status: 5`. Unary is `NOT_FOUND`. The stream is
    `zugrpc_error_protocol`, and `$status()` stays `NULL`.
  - **Header status skips the content-type check.** `content-type:
    text/html` with `grpc-status: 0` in the headers. Unary is the not-gRPC
    protocol error. The stream returns the message and ends `OK`.
  - **No body excerpt.** On the stream, the not-gRPC condition's `body` is
    always `raw()`. Unary keeps the first 1 KiB, straddled at 1023, 1024
    and 1025 bytes.
- Cause: the stream re-implements design §6.2's order in two places, and
  both drift from `unary_outcome()`.
- Fix: one resolver shared by both paths.
- Family: 3, the class fixed as an instance. Siblings checked: the eleven
  other error shapes the hunters tried agree on both paths.
- Test the suite lacked: the unary-against-stream differential, #64.

## 2. Deliver a stream's complete messages before raising on a bad frame — #76, medium, reproduced

- Where: [R/stream.R:240](https://github.com/pedrobtz/zugrpc/blob/90cc3c0/R/stream.R#L240),
  with `frame_split()` in [R/frame.R](https://github.com/pedrobtz/zugrpc/blob/90cc3c0/R/frame.R).
- Trigger: good messages and then a bad prefix (flag 2 or 7, or a length
  above `max_message`) in one DATA frame. The first read raises and the
  good messages are lost. With a 300 ms gap they are delivered first.
- Cause: `frame_split()` raises from inside its loop, so the messages it
  has already split from the buffer are lost.
- Fix: return the messages before the bad prefix, queue them, and raise on
  the following read.
- Family: none of the four; see Cross-cutting. Siblings: unary needs
  exactly one message, so it is unaffected.
- Test the suite lacked: `msg, msg, bad` in one read and one byte per read
  give the same messages, then the same error.

## 3. Resolve a stream's status before marking it done — #77, medium, reproduced

- Where: [R/stream.R:268-287](https://github.com/pedrobtz/zugrpc/blob/90cc3c0/R/stream.R#L268-L287).
- Trigger: trailers `grpc-status: 5` and a `-bin` trailer that is not
  base64, read under `tryCatch(warning = )` or `options(warn = 2)`. The read
  unwinds on the metadata warning. After that, every read returns `NULL`
  and `$status()` is `NULL`: a failed call reads as a clean end.
- Cause: `done` is set before the trailers are decoded and the status is
  recorded, and `stream_end()` is not guarded.
- Fix: resolve first, then mark done; or record the unwind.
- Family: 1. Siblings: an interrupt in the same window (by inspection).
  An undecodable details trailer keeps the status, because the status is
  set before that decode.
- Test the suite lacked: a non-OK stream with a bad `-bin` trailer, read
  under `warn = 2`.

## 4. A deadline or interrupt costs the channel its connection — #78 (upstream pedrobtz/zuhttp#338), medium, reproduced

- Where: zuhttp, reached from `grpc_call()` and
  [R/stream.R:327](https://github.com/pedrobtz/zugrpc/blob/90cc3c0/R/stream.R#L327).
- Trigger: `deadline = 0.3` against a server that stalls after its
  headers, on unary and on a stream. Also a real SIGINT during a blocking
  read, or `setTimeLimit()`.
- Recorded by the counterpart: EOF on the connection, no `RST_STREAM`, and
  the next call on a new connection. `$cancel()` gave `RST_STREAM(CANCEL)`
  and reused the connection. So did a deadline caught by zugrpc's own clock
  between reads.
- Cause: raw `zu_resp_read()` closes the connection on
  `zu_timeout_error` and `zu_interrupted_error`. zugrpc never calls close,
  so the letter of D8 holds. Design §6.6 ("aborts the request", "keeps the
  channel") does not.
- Fix: upstream; meanwhile a live test, and a note in §6.6.
- Family: 3. Siblings: a server `RST_STREAM` also closes the connection,
  and the two messages sent before it in the same read are lost.
- Test the suite lacked: a deadline inside a blocking read, against a
  server that logs frames.

## 5. Resolve the status before `RESOURCE_EXHAUSTED` on a large unary body — #79, medium, reproduced

- Where: [R/channel.R:75](https://github.com/pedrobtz/zugrpc/blob/90cc3c0/R/channel.R#L75),
  [R/conditions.R:84](https://github.com/pedrobtz/zugrpc/blob/90cc3c0/R/conditions.R#L84).
- Trigger: `max_message = 100` and a 503 HTML page of 300 bytes. Unary is
  `RESOURCE_EXHAUSTED`, the stream `UNAVAILABLE`. The same holds for a
  `text/html` 200, two small messages, or an oversize message with a
  non-OK status.
- Cause: `max_body` is meant to bound one message and its prefix, but it
  bounds the whole body, error pages included, and fires before any status
  is read.
- Family: 1.
- Test the suite lacked: a 503 larger than `max_message` is `UNAVAILABLE`
  on both paths.

## 7. Metadata named `r`, `re` or `req` breaks the call — #81, medium, reproduced

- Where: [R/call.R:115](https://github.com/pedrobtz/zugrpc/blob/90cc3c0/R/call.R#L115).
- Trigger: `metadata = c(req = "v")`. The result is `simpleError: expected
  a request from zu_request()`, and nothing is sent. Through channel
  headers, every call fails.
- Cause: `do.call(zu_headers, …)` lets a header name bind, by partial
  match, to the formal argument `req`.
- Family: none of the four; see Cross-cutting. Siblings: no other
  `do.call()` passes user names.
- Test the suite lacked: names that are prefixes of zuhttp formals.

## Cross-cutting

- **Two paths, one rule, written twice.** Findings 1, 5 and 12 are the
  unary and stream paths implementing §6.2 and §6.6 separately and
  disagreeing. The cheapest guard is one resolver both call, held to a
  unary-against-stream differential (#64).
- **zuhttp's validation leaks as a bare `simpleError`.** Findings 7, 8 and
  11 are values zugrpc accepts that zuhttp refuses later, outside the
  `zugrpc_error` hierarchy (D10). Finding 9 is the reverse: zuhttp
  defaults that zugrpc never meant to send. zugrpc's tests use the mock
  transport, which hides most of this.
- **A flag set before the state it stands for.** Findings 3 and 12: `done`
  is set before `status` and `error` are, and `channel$closed` is set
  before the streams learn of it. Every reader in between sees an
  inconsistent object.
- **Candidate rules for `correctness.md`**, to be proposed in
  `pedrobtz/packages`:
  - *Delivery must not depend on segmentation.* A parser that fails
    partway through a buffer first delivers everything before the failure
    point, so one read and one byte per read give the same result
    (finding 2). This is the streaming form of "what the caller got before
    the error", but none of the four families names it.
  - *`do.call()` with user-supplied names is argument matching on user
    data.* A name can bind, by partial match, to a formal of the callee
    (finding 7). Pass user data as one argument, never spliced into
    `...`.

## Held: what was probed and stood

The hunters' full lists are in their reports. In summary:

- **Emission**, recorded on the wire: pseudo-headers, `te`,
  `content-type` once, `grpc-accept-encoding`, user-agent order, the body
  prefix at 0, 3 and 100000 bytes, `grpc-timeout` at every unit edge and
  the cap, `-bin` base64 against jsonlite up to 300 kB.
- **Hostile session**: `LC_ALL=C`, `tr_TR`, `OutDec = ","`,
  `scipen = -5`, `digits = 3`, `warn = 2` (except finding 3) and a
  non-UTC `TZ` change nothing. So do 45,000 random `grpc_timeout()`
  values.
- **Decoding**: reassembly at every DATA segmentation, flags 0, 1, 2, 128
  and 255, `max_message` at 0, 1 and 100 straddled on both paths, lengths
  up to `0xFFFFFFFF`, read sizes around 64 KiB and 16 MiB, `grpc-status`
  spellings, the HTTP fallback map, status order, repeated received
  metadata, base64 edge cases, `grpc-message` percent-decoding, details of
  each type.
- **Sequences**: `RST_STREAM` and GOAWAY at each point, a second HEADERS
  block, DATA after trailers, use after end, cancel twice, close in every
  stream state, close twice, GC in every state, 2000 sequential and 50
  concurrent streams, real SIGINT, `saveRDS()` of channels and streams,
  fork with `mcparallel` and `mclapply` (the parent stays undisturbed),
  keepalive PINGs, process exit with an open stream.
- **grpc-go**: interop calls, `-bin` echo, every status, streams, and 30
  rounds of stall, cancel and call against `tools/test-server`.

## Not reached

- TLS (`https://`) on every slice; zuhttp's OpenSSL backend; Windows.
- Messages above 2^31 bytes in either direction, and the 4 GiB request
  refusal, for memory reasons.
- CONTINUATION frames, padded frames, header blocks above 16 KiB.
- Flow control under a slow reader, measured in bytes outstanding.
- A keepalive PING left unanswered.
- An interrupt landing inside the pure-R windows of `stream_take()` or
  `stream_end()`; inspection only.

## Not reproduced, and by design

Every reproduced trigger was re-run, and all reproduced.

- **By design:** a non-OK stream raises once and then returns `NULL`
  (§6.6, decided 2026-11-05).
- **By design:** `application/grpc-web` and `application/grpcx` pass the
  content-type check (§6.2: "starting with `application/grpc`").
- **By design:** a Trailers-Only `OK` on unary is a protocol error (§6.2).
- **By design:** a stall after part of the deadline overruns it
  (§6.6, zuhttp#173).
- **By design:** keepalive PINGs go out only before a call.
- **Not a bug:** each concurrently open stream gets its own TCP
  connection. This is zuhttp's pool, so D8's "keeps the connection pooled"
  is never exercised with two streams on one connection.
- **Not a bug:** GOAWAY with a `last-stream-id` covering the stream lets it
  finish `OK`. That is correct HTTP/2, and §6.1's "a GOAWAY fails in-flight
  calls" is the loose part.
- **Existing issue:** `saveRDS()` writes channel headers such as
  `authorization` in clear; commented on #56.
- **Existing assurance gaps:** a forked or deserialised copy of an open
  stream replays its buffered messages and then fails as `UNAVAILABLE`
  (#65, #66).
- **Surprises, not filed:**
  - a repeated `grpc-status` takes the first value, and grpc-go was not
    checked;
  - `grpc-encoding: IDENTITY` with the compressed flag is `UNIMPLEMENTED`,
    while lower-case `identity` is a protocol error;
  - server `RST_STREAM(ENHANCE_YOUR_CALM)` is `UNAVAILABLE`, so retry
    handlers will retry it.
